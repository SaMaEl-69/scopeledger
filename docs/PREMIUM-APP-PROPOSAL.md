# ScopeLedger premium application proposal

Prepared 5 October 2026. This is a proposal based on the three original build briefs, the current application source, the feature choices and the recorded acceptance evidence. The current brief/invoice refinement is authorized implementation work; the additional features below are recommendations for a subsequent decision.

The most useful next investment is dependable client documents, faster access to existing work and continuity while preparing a document. The mandatory operational application is already present. Invoices, manual payment tracking, the calendar and the agency toolkit should be improved from their existing implementations rather than counted as missing features.

The editor and PDF should use the same public document model and renderer. Readiness must explain what to fix, preserve entered text and focus a visible destination. Export failure must preserve the document and provide an honest retry route. Prior issued snapshots must retain their recorded values.

The tagged/outline API is supported by [Playwright's official PDF documentation](https://playwright.dev/docs/api/class-page#page-pdf). A structure tree or export option alone does not establish usable reading order or PDF/UA conformance. The final verification record should distinguish structural inspection from those unperformed checks.

For a future quick-find control, use an established keyboard interaction model such as the [WAI-ARIA combobox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), including predictable result navigation, selection and dismissal while preserving ordinary text editing. This is implementation guidance, not evidence that a custom widget is currently needed.

Avoid adding multi-line accounting, automatic tax rules, bank feeds or payment processing to this scope without a separate product decision: the current invoice represents an approved scope change and manual collection record. Likewise, cloud accounts/synchronization, automatic AI writing and automatic client messaging would change the privacy, operating-cost and workflow contract. Independent Agency devices remain independent unless the owner deliberately chooses a new synchronization model.

## UI quality bar for further work

Continue the existing restrained visual system. Use one type scale, consistent readable metadata, aligned form labels and predictable spacing. Keep the project/client/change context and save/approval status visible. A screen should make its next meaningful action clear; detailed financial explanations, planning controls and filter semantics can remain in accessible disclosures.

Prioritize task-specific density: readable decision forms, scan-friendly queues and document-like previews. On phones, long names, amounts and error messages should reflow, and controls should preserve their meaning rather than hide required information. Avoid adding themes, decorative charts or motion before a demonstrated task benefit.

Additional acceptance should include:

- Real focus navigation with sticky bars, dialogs and mobile navigation. Focused controls must remain visible; [WCAG's focus-not-obscured guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) describes the obstruction risk.
- User text-spacing overrides without lost content or function: line height 1.5 times the font size, paragraph spacing 2 times, letter spacing 0.12 em and word spacing 0.16 em. These are override tests, not mandatory default typography values. See [W3C text-spacing guidance](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html).
- Reflow at the narrow 320 CSS-pixel equivalent and a separate actual browser-zoom evaluation when available; [W3C reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) explains the relationship. Preserve necessary two-dimensional content deliberately rather than claiming all horizontal movement is forbidden.
- Empty, crowded, loading, error, locked, unsaved and restored states across every changed view. Reuse the established three-engine and responsive acceptance matrix, with unsupported emulation clearly labeled.

These checks complement the existing automated tests. They do not establish blanket accessibility or a promise of zero defects.

## Suggested sequence

1. Use the completed brief/invoice redesign, type-specific editors and actual protected PDF samples; review the fresh feature and visual acceptance evidence before choosing additional scope.
2. Address the owner-controlled launch gates in parallel with physical-device, assistive-reader and representative-PM evaluation. Keep live purchase availability closed until the external setup is verified.
3. Choose persisted document drafts first if reload loss is a real interruption; choose quick find next if record navigation is a frequent burden. Add a cross-project invoice worklist when collection review repeatedly requires switching projects. Implement each as a bounded release with backup/recovery and dirty-state coverage.
4. Use observed client-document repetition and PM follow-up routines to choose between billing presets and saved worklists. Assess added fields against the time they save and the mistakes they prevent.
5. Revisit selective handoff only with explicit demand, a complete transfer specification and agreed integrity/confidentiality tradeoffs.

Each release should preserve the landing page, existing IDs/history, decimal and approval contracts, immutable documents, ordinary backup recovery and fail-closed entitlement. Record what was implemented, what was actually exercised and what remains external or unverified. A premium result comes from making these existing tasks clear, reliable and pleasant, then adding features that resolve observed friction.
