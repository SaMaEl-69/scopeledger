# ScopeLedger security hardening

8 October 2026. The application has been audited and hardened locally before hosting and seller setup. Protected actions remain closed on the owner's demo preview. No deployment, real payment, public policy publication or owner-data reset was performed.

## Scope and result

Reviewed the built HTTP server, Vite private-file boundary, licensing/session service, Gumroad verification, client-document transfer/HTML, sandboxed PDF renderer, release/backup tooling, dependency lockfile, CI and deployment templates. Tested untrusted requests, malformed cookies, concurrent verification, upload exhaustion, hostile authored text, release tampering and genuine PDF jobs in isolated development databases and fresh browser profiles.

The important application-level gaps found in this pass are repaired. Hosting security still needs staging verification on the actual Linux host and HTTPS origin. This is source review and automated adversarial verification, not a guarantee that every possible vulnerability is absent.

## Current protective boundaries

Live session cookies use Secure, HttpOnly, SameSite=Strict and the __Host- prefix. Sessions are random, hashed in storage and bound to a signed browser/device cookie. Mutations require the configured Origin; cross-site API requests are rejected before device-cookie replacement. Paid PDF authorization is checked before and after rendering, including session changes during asynchronous verification. Device allocation and quotas use SQLite transactions; one/five allocation rules and outage/adverse-purchase handling remain tested.

The PDF endpoint accepts an exact, bounded client-facing schema. Private internal fields, remote image sources and executable uploaded SVGs are refused. Authored text is escaped; imported raster images have byte/pixel bounds. Chromium runs with its sandbox enabled, JavaScript disabled, outgoing requests blocked and licensing secrets omitted from its environment. Backend errors/events do not include request bodies, cookies, purchase keys, IPs or authored document text.

The limits are per process: 16 active API operations, eight provider checks and two renderer jobs/probes. Activation allows 16 KiB of JSON; release/project authorization 4 KiB; PDF snapshots 2,600,000 bytes. Node allows 16 KiB headers, 128 connections and 100 requests per keep-alive socket. Provider verification retains its existing network/body deadlines. Bounded work and timeouts follow [OWASP's denial-of-service guidance](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html); Node's transport controls are described in its [HTTP server documentation](https://nodejs.org/api/http.html#serverrequesttimeout). CSP is an additional layer alongside escaping and validation, as described by [OWASP's CSP guidance](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html).

## Required before the internet launch

1. Install and verify HTTPS, firewall rules, loopback-only application access, non-root service permissions, persistent private storage, Chromium sandbox and reverse-proxy headers on the actual host. Run nginx -t and prove the trusted client-address chain before enabling proxy trust. Re-test the per-address limits with normal shared-office traffic and deliberate overload. None of these host checks has been executed on this Mac.
2. Measure Linux export memory and maximum supported documents, then set host/service limits. Account for retries and transient readiness deferrals; do not restart a healthy service solely because it briefly returns checking_deferred during exports.
3. Establish an encrypted off-host backup destination, restricted administration, tested retrieval and alert delivery. Server backup bundles and browser JSON backups contain private data and are not encrypted by the export tools themselves. The existing encrypted provider-key column does not encrypt every database field or the backup bundle.
4. Verify real seller/product/receipt, refund/revocation and recovery behavior using an agreed procedure. Mocked and generated development purchases are not evidence of a real Gumroad checkout. Keep purchases closed until those checks and the existing policy/approval gates are complete.
5. Run the prepared CI on a real remote, maintain dependency/Node/browser updates, restrict deployment write access, and monitor busy responses, provider failures, disk usage and host memory. Checksum manifests do not protect against an attacker who can rewrite both the release and its manifest.

## Architecture limits to understand

Workspaces are local to each browser profile. Browser project limits and preview watermarks are client-side product controls, not tamper-proof DRM. The server independently enforces paid PDF access. A screenshot cannot be prevented by a watermark.

A copied session token alone fails without its signed device cookie, but theft of the complete valid cookie pair is session compromise. The device identity represents a browser profile; it is not hardware attestation. HttpOnly cookies do not secure an already compromised browser or operating system.

The application does not currently provide cloud accounts, shared agency workspaces, role-based team permissions or a hosted client-signing portal. Those would require new server-side ownership, authorization, recovery and security designs before implementation. See the production runbook for the remaining operational and commercial launch gates.
