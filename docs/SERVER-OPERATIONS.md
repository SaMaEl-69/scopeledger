## Choose a host that can run the application

The current production entry point is designed for a single Linux VM with an HTTPS reverse proxy. It binds `127.0.0.1`, serves built Home at `/home/`, the canonical workspace at `/workspace/`, shared assets and synthetic samples, and independently authorizes `/api`. `/` redirects Home and legacy `/app` links redirect into the workspace. Keep these routes on the same `https://scopeledger.site` origin so browser records and usable licensing cookies remain available. Local records do not transfer to another hostname, protocol or port; licensing cookies follow host/path and secure-cookie rules, with configured-origin checks enforced by the backend. Use Node 24 LTS; the package supports `^22.13.0 || >=24.0.0`. Install a supported local Chrome/Chromium and its OS dependencies. Run as a dedicated non-root user, with the database and secret outside served files and on persistent local storage.

The renderer explicitly enables Chromium's sandbox. Container deployment requires compatible user/namespace/seccomp settings; [Playwright documents these requirements](https://playwright.dev/docs/docker). The real target host remains untested. A failed sandbox launch must be fixed in the host setup, rather than weakening the renderer. Static-only hosting cannot run this backend or preserve activation state.

Render is an alternative requiring additional deployment work: [persistent disks require a paid service](https://render.com/docs/disks), and its [public web service must bind to `0.0.0.0` and the assigned port](https://render.com/docs/web-services#port-binding). The checked-in server binds loopback, so it is not a turnkey Render deployment. Disk persistence, browser sandbox capability and actual exports must be established on the selected service. An ephemeral filesystem is unsuitable for the license database. No hosting account eligibility, commercial contract, region, payment method or production availability has been verified for this owner.

Keep one application process. SQLite transactions enforce capacity across connections, but export concurrency and duplicate-job sharing are process-local. Multiple replicas need a separate design and verification. Configure reverse-proxy request limits, HTTPS, certificate renewal, upload/time bounds and logs that omit bodies, cookies, client IPs and authorization material. Preserve the browser's original `Origin` header. Forward Home, workspace, assets/samples and `/api` to that process. The homepage is the authorized copy in `home/index.html`; the supplied Downloads HTML remains the preserved reference. Do not expose the loopback server directly or split the workspace/API onto a different origin without a deliberate data/cookie migration plan.

### Configure the trusted local proxy

The backend keeps its 20-activation/hour limit. By default it counts the direct socket address, so every visitor behind a local proxy shares that address. Enable `SCOPELEDGER_TRUST_LOOPBACK_PROXY=true` in the private **live** server configuration only after the proxy replaces `X-Forwarded-For` with exactly one verified client IP. The backend accepts that identity only from a loopback peer. An arbitrary client header or forwarded chain must never reach it unchanged.

For a dedicated application HTTPS virtual host, an operator can adapt this Nginx location, alongside certificates and per-client edge limits:

```nginx
location / {
    proxy_pass http://127.0.0.1:4173;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header Origin $http_origin;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header Connection "";
    client_max_body_size 2600000;
    client_body_timeout 15s;
    proxy_read_timeout 60s;
    proxy_request_buffering off;
    proxy_buffering off;
    proxy_cache off;
    access_log off;
}
```

Use an overwritten transport address rather than `$proxy_add_x_forwarded_for`. Disabled request/response buffering avoids proxy temporary copies of private uploads/PDFs; HTTP/1.1 also preserves streaming for chunked uploads. These directives follow [Nginx proxy documentation](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [body-size controls](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size), and [access-log controls](https://nginx.org/en/docs/http/ngx_http_log_module.html#access_log), checked on 2026-10-05. This example has not been deployed or exercised through actual Nginx.

If another proxy/CDN fronts Nginx, have the operator establish its trusted client-address chain first; a shared CDN address still gives a shared allowance. Validate real clients and forged/chained headers on the target host before launch. Missing or invalid trusted identity fails activation clearly before quota is charged. Preserve the backend's loopback binding and protect the host from untrusted local processes; local transport trust does not authenticate a particular process. Use application events for monitoring, and review/redact other proxy/error logs so headers, client addresses and document content remain private.

## Monitor useful information without collecting private work

Set optional `SCOPELEDGER_LOG_EVENTS=true` to write sanitized JSON events to the server process log. Each event contains only `at`, a known operation (or `unknown`), HTTP `status`, a controlled error `code` and `durationMs`. PDF successes, failures and meaningful status failures are reported. Keys, cookies, device labels/identities, IP addresses, provider payloads, client text and financial content are excluded. Tests verify that exclusion. Do not enable proxy/debug middleware that logs request bodies or headers and defeats it.

Have the host operator configure alerts for process restarts, increasing error rates, long export latency, memory/CPU pressure, disk space, database/WAL growth, failed backups and HTTPS expiry. No external alerting service is configured by this repository. Review usage and bills at least monthly. Public license status in demo mode is expected to report inactive/unconfigured; that is different from the app being unavailable.

## Publish and recover updates

1. Ask users to export local project backups before a consequential update. Browser projects are separate from the server license database.
2. Back up the license database consistently, including its WAL state, and retain the **matching** secret separately in a protected store. Test a restoration copy; do not experiment on the only live database.
3. Build a separate staging release using `npm ci`, the lockfile and the supported Node version. Run unit/type/build checks, the isolated protected PDF QA, and browser workflows with copies of data. Inspect every newly rendered PDF page.
4. Keep the production secret, seller/product IDs and persistent DB path unchanged. Deploy as the same dedicated user, restart one process, verify HTTPS/status and an authorized actual export, then monitor errors. Retain the previous build and a compatible data backup for rollback.
5. If an update fails, preserve the current files/data and restore the verified compatible release/backup. Do not downgrade a newer data schema blindly or substitute samples. Document any deliberate migration before running it.

Build into a separate release directory and publish the complete Home/workspace HTML, assets/samples and server release atomically. The local build uses `emptyOutDir: false` to retain older hashed assets, but it still writes entry files and is not an atomic production release procedure. Do not build in the currently served directory. Retain previous hashed assets at their existing public URLs for an agreed transition period: an already open older entry bundle may request one of its lazy view chunks later. A release-directory swap alone does not preserve those URLs; the deployer must retain/merge the hashed asset set or provide an equivalent serving arrangement. The built server serves entry HTML with `no-cache` and static assets with a one-hour cache, but open tabs may last longer than that cache lifetime. Preserve `/app` compatibility redirects and the same canonical origin when publishing.

An unavailable optional view/dialog now displays recovery controls while keeping the header, navigation and core workspace mounted. Navigate to the core workspace or Settings and export current workspace edits before deliberately reloading. There is no automatic reload or fake retry of a cached rejected lazy import. A workspace backup includes saved records/current core edits; it includes saved document drafts as of 8 October 2026, but does **not** include unfinished composer/comparison entries, which reload clears. The fallback explains that limit. This handling is a recovery measure, not a substitute for an atomic deployment and old-asset retention.

### Earlier live-cookie upgrade

This release changes live cookie names from `scopeledger_session` / `scopeledger_device` on `/api` to their secure `__Host-` names on `/`. The backend does **not** automatically accept or migrate the old names. If an earlier version was actually deployed, its existing browser may receive a fresh device identity after this update while its previous slot remains active in SQLite. Re-entering the key could then report full capacity, or consume another Agency slot. No earlier live deployment exists in this verified workspace; local-test cookie names are unchanged.

Before updating an older live deployment, have customers use **Release this browser/device** in that version while their existing activation still works, then reactivate in the updated version. Retain the database, matching secret and seller/product IDs throughout. If the upgrade already happened or the old browser is unavailable, independently verify purchase ownership and identify the particular previous device, then use the targeted seller recovery procedure in [server configuration](SERVER-CONFIGURATION.md). Reactivate using the matching key afterward; keep the other devices and durable recovery audit intact. Do not delete license rows, reset all activations or regenerate the secret to handle this transition.

At the same canonical origin, changing API cookie names does not change IndexedDB project data, drafts, approvals, payments or issued snapshots. Do not clear cookies or site storage as an upgrade step. If the origin itself changes, export and restore a verified project backup deliberately; browser storage does not move to another origin automatically. Stage this transition with a copy of the older database before any future live upgrade and communicate the required reactivation to affected customers.

Browser schema/migration recovery is documented in [owner operations](OWNER-OPERATIONS.md) and the [data audit](PART3-DATA-AUDIT.md). The licensing database currently creates its five tables additively with `CREATE TABLE IF NOT EXISTS`; this audit does not change their schema or reset records. Future column/schema changes need a reviewed transactional migration and restoration test. Historical quota/session rows are retained rather than silently deleting entitlements; monitor their growth and have an operator review safe retention of expired counters/sessions, while preserving devices, licenses and recovery evidence. No automatic retention job is claimed.

Patch Node, dependencies, Chrome and the OS on a staged schedule; rerun the protected renderer checks after Chrome/OS updates. The audited dependency upgrade is recorded by the root verification document. Encryption-secret rotation requires a deliberate re-encryption/identity/session migration or recovery plan; generating a new random secret is not a rotation procedure. A suspected exposure requires stopping protected access, preserving evidence privately and involving the operator, rather than printing the secret or replacing the database.
